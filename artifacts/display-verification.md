# 表示追従の検証

## 結果と原因

Godotの埋め込みゲームビューはFixed Sizeだと、外側を全画面にしてもゲーム自体を1440x810へ固定する。
今回のMacで同じ症状を実際に再現した。
作業先のプロジェクト別設定をKeep Aspect Ratioへ変えて再起動すると、同じ全画面操作でゲームバーの表示寸法が4442x2499へ増え、BUILD全体も拡大した。
ゲームが制御できる表示領域と、エディターが提供する表示領域は別である。
公式の[埋め込み表示の説明](https://docs.godotengine.org/en/stable/tutorials/editor/game_embedding.html)も、固定サイズと追従サイズ、埋め込み中の全画面切替の制限を区別している。

プロジェクト設定のcanvas_itemsを維持し、keepとallow_hidpiが有効であることを確認した。
この2つの既定値を一度明記したが、Godotが再読み込み後に既定値を正規化して除去するため、project.godotの最終差分はない。
最終状態の実Windowでも拡縮が有効であることを自動検査で確かめた。
ゲーム内でOSのDPIやroot.scaleを追加して拡大する処理は入れていない。
マウスは後からポーリングしたカーソル位置を使わず、そのイベントの論理座標を使用する。
フォーカス喪失でホバーとGUIフォーカスを解除し、未確定の経路を保ったまま復帰できる。
戦闘ルール、固定式、保存形式は変更していない。

## プロジェクト別のGodot設定

この作業先の.godot/editor/project_metadata.cfgのgame_view/embed_size_modeを1にした。
設定名はGodotの[公式ソース](https://github.com/godotengine/godot/blob/master/editor/run/game_view_plugin.cpp)と、実際にインストールされたバイナリ内の設定名を照合した。
元の内容はartifacts/runtime/editor-metadata-before-display-1794712632850.cfgへ退避し、他の設定を維持した。
Godot全体の設定とOSの表示設定は変更していない。

.godotは生成物としてGit管理していない。
新規インポートや生成キャッシュ削除後は、ゲームビュー右上のメニューでFixed SizeからKeep Aspect Ratioへ選び直す。
独立実行ではこのエディター設定は関係なく、ゲーム内SETTINGSで全画面へ切り替える。
READMEに両方の手順を記録した。

## 自動検査

tests/display_flow.gdを通常のscripts/check.shへ追加した。
実際のWindow、main.tscn、Controlを生成し、物理ウィンドウ座標のイベントをGodotの入力パイプラインへ送る。
GUIボタンも押下信号を直接呼ばず、拡縮された座標のマウス入力を通す。

| 確認対象 | 検査 |
| --- | --- |
| 基準と縮小と拡大 | 1920x1080、1440x810、1280x720、3840x2160 |
| 異なる縦横比 | 1600x1200、2560x1080、1200x1600 |
| 余白と正方形 | 独立計算した一様倍率と中央位置、論理画面1920x1080の維持 |
| GUIと盤面 | BUILDの開始、(4,4)の選択、終点ダブルクリック、行動ダイアログ |
| 余白の入力 | 経路と選択が変わらない |
| リサイズ往復 | 経路を保って拡大、追加、元へ戻して確定 |
| フォーカス | ホバー解除、非アクティブ時の入力拒否、経路再開、GUIボタンの継続操作 |

61チェックが成功した。
拡縮そのものは既存のGodot機構で最初から成功しており、独自の拡縮器を作ったわけではない。
1200x1600では理想の余白462.5が物理ピクセル463へ丸められるため、期待値も独立計算した最寄りの物理ピクセルとした。
既存の最小ウィンドウ幅未満の寸法はOSがクランプするため、縦長の検査も最小幅以上で行う。

旧main.gdの隔離複製に同じ61チェックを実行すると24件失敗した。
拡縮後の盤面入力、イベント座標、フォーカスの不備を検出しており、証拠はdisplay-red.txtに保存した。
アスペクト比を無視する誤設定を検証専用プロセスへ注入した場合も、倍率、余白、論理寸法などの検査が失敗した。
証拠はdisplay-aspect-mutation.txtに保存した。
この誤設定は製品へ保存していない。

## 実画面の観測

Godot 4.7.2、Compatibility、Apple M4、macOSでCUAによる実際のクリックを行った。
Godotの画面APIで表示倍率2.0、168dpi、画面4608x2592を取得した。
出力はhidpi-probe.txtに保存した。
このプローブのwindow=(100,100)は初期化時の一時Windowであり、実プレイのウィンドウ寸法ではない。

| 実際の表示 | 観測 |
| --- | --- |
| 埋め込み1438x809 | BUILDと全ペインが収まる |
| 修正前の埋め込み全画面 | ゲームバー1440x810のままで大きな周辺余白が残る |
| 修正後の埋め込み全画面 | ゲームバー4442x2499へ追従し、BUILDの文字とリングと入力欄が拡大する |
| 独立1600x900 | ゲーム内SETTINGSをクリックして開ける |
| 独立全画面4608x2592 | BUILD、開始ボタン、盤面、リング、波形、フッター、行動ダイアログが拡大する |
| 独立縦長2304x2366 | 上下に各535ピクセルの余白、中央に2304x1296の16:9画面が収まる |
| 元の1600x900へ復帰 | 確定済みの行動ダイアログと位相と行動状態を維持して縮小する |

独立ウィンドウのスクリーンショットはタイトルバー64ピクセルを含む。
縦長の画像寸法2304x2430からこれを分け、表示領域を2304x2366として記録した。
全画面と埋め込みのゲームバーの寸法を混同していない。

実操作では全画面で(4,4)、(5,4)へ経路を選び、終点をダブルクリックして行動ダイアログを開いた。
DAMAGEでAを攻撃し、敵合計HP189/200と02への手番更新を確認した。
ウィンドウへ戻した後に02の経路を1歩選び、縦長へ変更して続きを追加し、2歩目で確定できた。
上下の余白のクリックは経路を変えず、モーダルも中央へ収まった。
Aの経路選択中に最小化し、Raiseで復帰した後もPATH1を保持し、続きを追加してPATH2の行動選択へ進めた。
元の寸法へ戻してもその行動ダイアログを操作できた。

最後にGodotエディターを元のPHASEプロジェクトで開き直し、エディターから実行して追従する全画面BUILDを確認した。
SAVEを操作しておらず、既存のユーザーセーブは変更していない。
スクリーンショットはその場で観測し、画像ファイルとしては保存していない。

## 限界と最終確認

独立1920x1080と1440x810を厳密に同じ実機条件で見比べるNREQ-001-S01は未確認のまま残す。
両寸法の実Window変換とGUI入力は自動検査で確認し、実画面では論理1920を1600、4442、4608などへ拡縮した配置を観測した。
他OS、倍率1.0や1.5のディスプレイ、複数画面間のドラッグ移動は実機未検証である。
4:3と横長の倍率と入力は自動検査で確認し、実機で確認した異なる縦横比は縦長である。
回復偏重による長期化など、既存のゲームバランスの評価はこの変更で変わらない。
未確認の状態とユーザーの最終確認はopenspec/manual-checks.mdへ記録した。
追加アプリを導入せず、Godot、許可済みNode.jsとGitだけで作業し、外部へのpushと公開はしていない。
