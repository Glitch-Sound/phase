# 小さい円弧の描画不具合と検証

## 判断と範囲

基準はe77c381であり、作業開始時の追跡ファイルに変更はなかった。\
既存のREQ-030-S02のHP比率、REQ-030-S03の判別性、NREQ-001-S03の拡縮表示に反する描画不具合として直接修正した。\
正式仕様のシナリオは変更せず、テストを先に追加して失敗を確認した。\
追加のOpenSpec changeは不要と判断した。\
共通の細線描画の方針はopenspec/tech.mdの表示原則へ反映した。

## 切り分け

Godot 4.7.2、Apple M4、Compatibilityレンダラーで原寸の描画を調べた。\
修正前のdraw_arcにもアンチエイリアスtrueと正の線幅を指定しており、既定値がオフのままという仮説は該当しなかった。\
PNGへの保存前のGPU画像でも、HP100の白線に欠損があった。\
等倍の孤立した円弧では、盤面とTURN ORDERのいずれも円周の約6度で白線が消えた。\
実際のウィンドウ縮小を使った回帰検査では、位置のサブピクセル位相によって欠損がさらに増えた。\
低HPが完全に消える場合もあった。\
そのため、チャット画像の縮小や圧縮だけでは説明できない。

従来のHP線幅はTURN ORDERで0.65論理px、盤面で0.682論理pxだった。\
最小画面の倍率0.6では約0.39物理pxと0.409物理pxになり、既存の細線描画で不均一と欠損が生じた。\
頂点数だけを変えても解消しなかった。\
最小の物理線幅を確保すると欠損がなくなったため、主因はサブピクセルの細線描画と判断した。\
これは当該環境での観測であり、Godot全般の既知不具合として断定しない。

PNGを保存して再読込した画像と、保存前のGPU画像は全画素一致した。\
保存時のPNG圧縮による画素の欠損はなかった。\
チャット側のプレビュー縮小は制御していないが、原寸PNGの段階で起きた不具合を修正した。

## 修正

- HP線は最低0.9物理px、色リングは最低1.1物理pxを確保する。\
  大きい表示では従来の線幅を維持し、小さい表示だけ補正する。
- 円弧の分割は固定3度刻みから、物理的な弦誤差0.03px以下で決める方式へ変更した。\
  半径、領域の角度、隙間、HPの角度は変更しない。
- 倍率はCanvasItemのビューポート変換と自身の変換から得る。\
  OSのDPI倍率を追加で掛けない。
- 値はgame/tuning.gdに集約し、ui/visuals.gdの共通描画から適用する。
- COREを基準にした間隔、盤面中央と大きさ、白と5色、名前、ルール、数式、保存は維持した。\
  他のUIや波形の描画は変更していない。

## テストと誤りの検出

| 検査 | 結果 |
| --- | --- |
| 描画部品のテスト | 修正前は未実装として失敗し、修正後は109件成功した。物理線幅、弦誤差、入力の不変性を検査した |
| 修正前の実描画 | 216件中76件が失敗し、HP1の消失とHP50、89、100の欠損を検出した |
| 修正後の実描画 | PNGの再読込確認も加えた240件すべてが成功した |
| DPI二重適用の変異 | 製品を変更せず検証用コピーで誤りを入れ、240件中76件の失敗を検出した |
| GPUなしの誤実行 | headlessでは終了コード2として拒否し、画素を未検証のまま成功扱いしない |
| 全体検査 | npm run checkが成功した。1,114件の検査と戦闘再生、4仕様の厳密検査が成功した |

実描画の回帰検査は、6倍率(0.6、0.75、1、1.25、1.5、2)、4ユニット、盤面とTURN ORDER、HP1、50、89、100を対象とした。\
HP0の画像との差分から白線だけを取り出し、描くべき円弧の欠損と、HP不足の区間への意図しない描画を区別した。\
HP100は一周、HP50と89は比率どおりの空白、HP1は短い正の線があり、欠損も不足区間への描画も0だった。\
HP0を誤って満タンで描けば差分が消え、HP100の確認が失敗する。\
HPの端付近はアンチエイリアスの物理的な幅だけを除外し、角度の期待値は描画関数から生成していない。\
位置と倍率で欠損の有無が変わったため、4体の実際の画面位置を組み合わせて検査した。

プロダクト検査scripts/check.shへarc_strokesを追加した。\
実GPUが必要な画素検査は、headless検査とは分けて次のコマンドで明示的に実行する。

```sh
godot --path . --script tests/arc_render.gd --resolution 1920x1080 --log-file "$PWD/artifacts/runtime/arc-render.log"
```

## 描画負荷

tests/arc_performance.gdで同じTURN2を、修正前、修正後、修正後、修正前の順に2回測定した。\
修正前の描画本体はe77c381から再現し、アンチエイリアスtrueと正の線幅を含めて比較した。\
半径、角度、色、波形と他UIを同じにし、各区間は15フレームの準備後に90フレームを観測した。\
通常の約30Hzを目標とする再描画制御は維持し、各区間に21から25回の実描画があった。

| 実画面 | 方式 | UI描画CPU中央値 | 円弧部分のCPU中央値 | UI描画CPUのP95 |
| --- | --- | --- | --- | --- |
| 1920x1080、倍率1 | 修正前 | 5.829から6.036ms | 1.249から1.310ms | 6.095から6.764ms |
| 1920x1080、倍率1 | 修正後 | 5.754から5.776ms | 1.216から1.226ms | 5.949から6.038ms |
| 4608x2592、倍率2.4 | 修正前 | 6.095から6.614ms | 1.299から1.434ms | 6.384から8.918ms |
| 4608x2592、倍率2.4 | 修正後 | 5.877から6.187ms | 1.248から1.437ms | 6.395から6.622ms |

この測定では大きなCPU負荷増は見られず、30Hzの再描画目標に対して余裕があった。\
全画面のエンジンFPSは修正前約95から121、修正後約90から96で揺れ、各回の最後の修正前も約95から96だったため、FPSの差を修正だけの効果とは判断しない。\
UI描画CPU時間はコマンド生成の時間であり、GPU単体の実行時間ではない。\
共有Mac上の短時間測定であり、統計的な性能保証や他GPUの結果には広げない。\
再描画が観測できない場合は終了コード2とし、0msとして成功扱いしない。\
全16区間の値はartifacts/arc-performance-results.jsonに保存した。

## 限界

実GPUの結果は当該MacとCompatibilityレンダラーでの確認である。\
自然な一戦の攻略や、他のOSとGPUでの実表示の保証には広げない。\
小さい表示の低HPは短い線であり、正確なHP数値は右詳細で読める。\
チャットの縮小プレビューでは線が小さくなるため、意匠の最終確認はLibraryの原寸画像と実ゲームで行う。\
既存の全体実機確認7件は未確認を維持し、今回の円弧確認で全UIの確認済みへ変更しない。\
追加アプリ、push、公開は行っていない。
