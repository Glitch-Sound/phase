# 手番追従と対戦テンポの検証記録

## 現在の状態

2026-11-17に改修、自動検査と実Godotの一戦を実施した。
利用者の追加指示に従い、固定戦術の勝敗、決着手数と回復回数を合否から外した。
基本ルールの検査を維持し、npm run check、差分strictとstrictトレースが成功した。
平均10から15手は観測の目安であり、合格条件ではない。

## 表示と操作

三角とその寸法定数を除去した。
移動の終点で使う既存の_draw_cell_focusを、同じ色、線幅、角の形で現在手番のセルへ使う。
新しい枠や点滅は追加していない。
明示的な別ユニットの選択と未確定経路がある時は従来の選択、終点枠を優先する。

turnとactorの組が変わった時だけ、古い選択、タイムラインとセルのホバーを解除する。
開始、人の行動後、CPUの進行後、入力前とフレーム更新が同じ入口を使う。
同じユニットの連続手番もturnで区別する。
同じ手番中は他ユニットの確認を保持する。
PREVIEWは行動者の経路予測、INFORMATIONは明示選択がある時はそのユニット、既定では行動者を示す。
CPUの結果演出中も、前の演出主体ではなく実際の次のactorを追従する。
停止中のCPUでも任意確認はでき、停止だけで選択を解除しない。

既存の1000px盤面、タイムライン、配色、HP円弧、経路再選択、右下メニューは維持した。
最後の1体への救済は追加していない。

## 手の定義と比較条件

両陣営合計で、1ユニットの移動と行動またはWAITを1手と数える。
移動で終局した場合も1手であり、経路のクリック、BACK、考慮と演出の実時間は数えない。

scripts/tempo-study.pyで旧コミット2017a4a1781c39451a0870adced066fc3155468fのgameソースと現行ソースを隔離して比較する。
全コピーの原本SHA256、全条件の結果と手数をartifacts/turn-tempo-comparison.jsonへ記録した。
再実行はpython3 scripts/tempo-study.pyで行う。
この比較は通常のnpm run checkとは別の追加分析である。
プロダクト検査にはturn_followとtempo_riskをscripts/check.shへ追加した。

36条件の内訳は次のとおりである。

- 初期の役割配分は4ステージとシード1、128、729、7、2026の20条件。
- 均等配分は4ステージとシード128の4条件。
- REVERSEとGEARのLSRIVは4ステージとシード128、2026の8条件。
- 初期配分でPLAYERだけ反撃重みを0.4倍にした攻撃的な方針は4ステージとシード128の4条件。

両側とも合法な経路、パネルとスキルを同じ評価器で選ぶ。
攻撃的な方針以外の戦術の多様性は限定的であり、人間36人分の対戦を意味しない。
初回24条件で候補を比較し、追加12条件でも同じ候補を確認した。

## 実Godotでの一戦

macOSのGodot 4.7.2で、隔離したcpu_manualシーンを新しく起動した。
シード1、初期の役割配分、初期装備、初期HPから、PLAYERを手動で操作してENEMY CPUと最後まで戦った。
CPU速度は1xで、HPや盤面を途中で注入していない。
17手でVICTORY、残りHPはPLAYER1が5、PLAYER2が19、AとBが0となった。
人が10手、CPUが7手を行い、全17手が移動と攻撃で、回復とWAITは使わなかった。
PLAYER1には16手目と17手目の連続手番があった。
実操作の経路、行動と全履歴はartifacts/turn-tempo-native.jsonに記録した。

攻撃量は序盤11から27、中盤に40、最後にINFが揃った84へ変化した。
低HPの5を残した連続手番から決着し、手番と位相の一致が結果につながる場面を観測した。
主観的には旧27手の一戦より圧縮され、被弾を放置しづらく、最後の位相一致の強さが読み取れる。
一方で、回復を選ぶ余裕が少なく、自然な回復戦をこの一戦で確認したとは言えない。
実時間は検証の読み取りと道具の往復を含むため、通常プレイヤーの所要時間として集計していない。
CPUの経路から対象、効果までの提示と操作の占有は観測したが、全ハードウェアで毎手1から2秒を保証していない。

## 対戦検査の整理

旧固定戦術はバランス変更により14手のDEFEAT、双方回復0になり、旧期待に対して失敗していた。
利用者は今後も調整するため、こうした固定期待を外すよう明示した。
新しい勝敗や回復回数へ期待値を差し替えず、contested_play、panel_play、playthroughとcpu_playから戦術の勝敗、特定予算内の決着、回復回数と反復回数の合否を外した。
両陣営の回復を強制するために追加していたシード3の代表ケースも除き、新しい代表ケースは追加していない。
勝敗、回復と反復は既存の結果記録に観測として残す。

再生では既存の経路と行動の適法性に加え、共通の基本契約でHPが有限かつ0から最大値の範囲にあること、継続時は1手だけ進み、終局時はRESULTとなることを確かめる。
再生予算は実行量だけを制限し、未決着でも基本ルールを守っていれば失敗にしない。
勝敗条件そのものは既存の直接条件検査で維持し、放置戦でも目標へ実際に着いた瞬間のMOVEとENDを区別して検査する。
数式と対象、HP上限、順序と保存境界の下層の検査は除いていない。

旧decision_captureは新しいturn_tempo_captureへ接続し、消えた三角と過去の対戦の固定HPへ依存しない。
現行のGPU再生も合法な現在の選択を入力して確認し、過去の勝敗、手数と最終HPへの固定を外した。
過去の手動戦はartifacts/turn-tempo-native.jsonの観測記録として残す。
以前の画像比較専用ラボは旧場面の資料であり、npm run checkのバランス合否には使わない。

この検査変更は既に基本ルールを守るモデルに対して最初から成功した。
その後にHP上限超過を作る誤実装と、手番を2増やす誤実装を一つずつ入れ、いずれも基本契約の失敗で検出した。
誤実装は毎回元へ復元した。
さらに攻撃36、回復48、位相幅0.75へ一時変更した状態で、4つの対戦スイートの基本ルール検査が成功した。
この一時値は選択したバランスではなく、検査の結合を切れたことを確かめる診断であり、最終コードは攻撃72、回復24、位相幅0.85である。

診断中は、検証用の守備方針が全候補を除外して合法経路を閉塞と誤認する問題を発見した。
検証用の方針だけを修正し、絞り込みに合わなくても合法経路がある場合は移動して待機する。
ゲーム本体の選択ルールや移動規則は変えていない。

## 最終検査とverify

npm run checkは全スイートと5仕様のstrictで成功した。
プロダクト検査の入口はnpm test、全体検査の入口は従来どおりnpm run checkである。
今回はscripts/check.shへ手番追従と危険評価のスイートを加え、既存の再生の合否を基本契約へ整理した。
実GPUの最終検査は166検査成功であり、既存4サイズの操作と基本契約を確認した。
平均と分布を得る36戦は別の分析コマンドであり、通常検査のケースを増やすためには使わない。
