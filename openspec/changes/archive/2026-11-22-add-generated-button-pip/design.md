# 設計

## 背景と制約

- 提案: [proposal.md](proposal.md)
- 前提: openspec/tech.md の 技術上の判断基準 と テスト方針
- Button、CheckButton、OptionButtonと候補一覧は複数の場所で動的に生成される。
- 既存のゲーム内音量UIはなく、SFX有効フラグとMasterを使う。

## 設計判断

### D-01 - GUI入力と押下信号を共通部品で対応付ける

- 選択: ui/sfx.gdが画面配下のBaseButtonとPopupMenuを監視する。\
  有効なGUI押下と同じ更新の成立信号を1回だけ消費する。\
  PopupMenuでは確定信号の後に入力通知が届くため、同じ更新の遅延呼出しで照合する。\
  メタデータで同じ部品を二重接続せず、後から加わる候補も監視する。
- 理由: 各画面の操作コールバックを変えず、内部の信号再送と値更新を無音にできる。
- 代替案: 各ボタンのコールバックへの重複追加、ホバー音と全入力に反応する音は採用しない。
- 昇格: openspec/tech.md の 技術上の判断基準

### D-02 - 短いPCMを一度生成して再利用する

- 選択: game/tuning.gdに長さ0.032秒、周波数880Hz、立ち上がり0.003秒、減衰0.012秒、標本化44100Hz、ゲイン-30dBを定義する。\
  モノラル16bitのAudioStreamWAVを準備時だけ生成し、両端を0へ滑らかに落とす。\
  専用の単声レーンからMasterへ送り、戦闘状態のリセットでは短いUI音を切らない。
- 理由: 外部素材とファイルを増やさず、音のクリックと耳障りな重なりを避ける。\
  既存の戦闘音のレーンと音量へ影響しない。
- 代替案: select.oggの復活、実行ごとの生成とグローバル音量の変更は行わない。
- 昇格: openspec/tech.md の 技術上の判断基準

## 検証計画

| シナリオID | 設計判断 | 検証方法 |
| --- | --- | --- |
| REQ-054-S01 | D-01 | 自動テスト |
| REQ-054-S02 | D-01 | 自動テスト |
| REQ-057-S01 | D-02 | 自動テスト |
| REQ-057-S02 | D-01、D-02 | 実機確認 |

音声部品を実GUI入力で検査し、静的と動的なボタン、キー、取消と重複を同じ層で観測する。\
実画面との接続は代表だけを確かめ、既存の盤面とCPUの回帰を維持する。\
既存メニューの接続数1個という旧前提は、元の操作と生成音の厳密な接続集合へ更新する。\
既定の検査コマンドを変えず、バランス期待値を増やさない。\
通常Godotでは実ミックス信号の長さ、選択数と波形の両端を確認し、聴感とは区別する。

## リスクと移行

発音要求と機器から聞こえる時刻は異なり、好みと物理機器の確認を台帳へ残す。\
終了するアプリで短い音の出力完了を待つ処理は加えない。\
保存の変更と移行はない。
